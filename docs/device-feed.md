# Personalized device feed — 2026-10-31

## Implemented behavior

The network task initializes Wi-Fi as before and loads a bounded identity record from the independent `device-auth` NVS partition, namespace `identity`, string key `record`. It validates the device UUID and existing `dev1_` credential format before requesting `GET /v1/device/feed` with `Authorization: Bearer <token>`. Only the credential selects identity server-side; no device-ID header or stop query is sent. The UUID is retained for local identity integrity, not authorization. Stop IDs, modes and order come exclusively from the v1 response. The portable model/parser and renderer remain provider-independent; no provider API data enters firmware.

Wi-Fi captive portal, recovery, BOOT handling, rendering, brightness, panel timing, fixture modes and display driver are unchanged. The client preserves the configured HTTPS origin and root certificate, bounded response capture, ten-second timeout, redirect refusal, and the existing background task/mailbox schedule.

Success polls every 30 seconds. Network, invalid/oversized feed and HTTP errors wait 60 seconds (client allocation failure retains the existing 30-second default). Authentication 401/403 waits five minutes and shows AUTH. HTTP 409 is normal missing/invalid backend configuration: ADD STOPS, retry in five minutes. Existing bounded Retry-After delta-seconds handling can increase these waits up to one hour. A valid empty v1 stops array replaces the old snapshot and shows ADD STOPS. Partial/upstream-error stops use existing v1 status rendering. Malformed responses never replace the last valid snapshot. Other temporary errors preserve arrival expiry and the existing 120-second stale limit; AUTH and configuration-required states hide old arrivals while retaining the snapshot in RAM. A valid new response replaces it atomically. No persistent stop cache was added: after reboot the device waits for a fresh backend feed, avoiding stale predictions or a second stop-selection source.

Missing/corrupt identity or absent HTTPS trust shows CONFIG and sends no requests. Wi-Fi setup/recovery continues; after offline identity provisioning, reset to reload. No serial provisioning commands or new browser fields were added. SDK logs remain suppressed and application logs never include credentials, identity records, headers, URLs, raw bodies or exception details.

## Provision the existing identity without compiling it

Device A was selected from the backend's ignored mode-0600 `data/device-deployment-private/test-identities.json`. Its existing credential was reused without regeneration, revocation or database writes. Its configured order is Metro physical station 6660122, then bus 94. Neither identifier is embedded in firmware.

Install the pinned development requirements. `tools/prepare_device_identity.py EXISTING_CREDENTIAL_JSON OUTPUT_BIN` reads the protected existing `{deviceId, token}` file and uses Espressif's NVS image generator. Paths, never tokens, are command arguments. The output directory must already be private (0700); the input must not be group/world accessible. Output is exclusive-created, mode 0600, size 0x6000. Temporary CSV/image files remain in a private directory and are removed on completion/failure; upstream diagnostics are suppressed. The tool never connects to hardware, contacts the backend, generates credentials or overwrites an existing image. Keep the entire output outside tracked firmware sources, in ignored protected storage. Do not commit, attach, print or distribute the image: it contains a plaintext bearer credential.

Prepared locally: `live-transit-feed/data/device-firmware-private/device-a-auth.bin` (ignored, 0600, parent 0700). Existing credential files are unchanged. The image contains no Wi-Fi credentials. Ordinary firmware builds contain no device token.

A one-time firmware **and partition-table** flash is required for this integration; it does not provide OTA. The new `device-auth` partition occupies 0x410000–0x415fff, beyond the unchanged factory application at 0x10000–0x40ffff. Wi-Fi NVS remains at 0x9000–0xdfff. Separately write the reviewed private 0x6000-byte image only at 0x410000, after explicit flashing approval and checking the connected board's flash capacity and partition layout. Do not erase the whole chip, overwrite Wi-Fi NVS, use a merged full-flash image, or write the private image on routine firmware updates. Before any identity write, inspect whether that partition is already provisioned; never replace an existing identity without authorization. No hardware writes were performed in this experiment.

## Security findings and limits

Source inspection: ESP-IDF HTTP client receives `cert_pem`; hostname verification is explicitly enabled, auto-redirect is disabled, and polling waits for SNTP synchronization. No insecure flags or certificate-validation bypass were added. The installed ESP32-S3 SDK has no ESP_TLS_INSECURE/SKIP_SERVER verification flags enabled. The existing local PEM is ISRG Root X2 (valid 2020-09-04 through 2040-09-17); it is a single configured trust root, with no automatic root updates. Chain changes may require a new public trust configuration/firmware. Revocation/OCSP checks are not configured. SNTP is unauthenticated and a usable clock remains necessary. On-device handshake validation is still pending.

Storage separation is not physical secrecy: this experiment uses unencrypted NVS and ordinary flash; secure boot, flash/NVS encryption, debugger/readout protection and a secure element were not enabled or validated. Physical flash access or compromised firmware can recover the bearer token, which also exists in RAM during requests. Host image/credential protection depends on filesystem access and backups; temporary-file removal is not guaranteed secure erasure on SSDs. Future partition changes/full-chip erase can destroy identity. No credential rotation, ownership or pairing workflow was added.

Backend inspection and existing deployment tests establish that device credentials only read their personalized feed, cannot use development-token routes, and cannot provision or write configuration/ownership. Management remains a separate trusted local/database operation. No backend contract, deployment, migration or secret changes are required.

Official behavior references checked 2026-10-31: [Espressif NVS generator](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/storage/nvs_partition_gen.html), [generator package](https://github.com/espressif/esp-idf-nvs-partition-gen), [ESP HTTP client certificate options](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32/api-reference/protocols/esp_http_client.html). Local SDK headers were also inspected; documentation alone is not physical test evidence.
